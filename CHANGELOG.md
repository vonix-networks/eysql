# Changelog

## 0.1.0 (unreleased)

First release.

- Defaults follow the YugabyteDB JDBC smart driver wherever an option has a counterpart there: `load_balance` is off, so a pool without it uses the configured hosts only, with no discovery; `connect_timeout` is pgjdbc's 10 seconds; `database` is the username. `username` (`yugabyte`) and `application_name` (`eysql`) keep eysql's own values.
- With `load_balance` on, server discovery with `yb_servers()` at start, every `yb_servers_refresh_interval` (0 to 600 seconds, where 0 reads it again as each connection opens) and after connection failures. On PostgreSQL, the configured hosts. A discovery asks the configured hosts first, each once, then the servers that are not down, as the JDBC driver's refresh does, and never dials a server that is down. A discovery that fails leaves the refresh due, as the JDBC driver's does: the next connection opened tries again, at most once a second, and otherwise the next refresh on the timer. `eysql_cluster:connect/1` waits for the first discovery, as the driver refreshes before its first pick.
- Least-loaded placement with the smart drivers' `load_balance` modes, as atoms or in the drivers' spellings, `topology_keys` preference levels and `fallback_to_topology_keys_only`, in the order the drivers document for each mode. A tie between equally loaded servers goes to one at random, as in the JDBC driver. Topology keys match cloud, region and zone in any case, with a Unicode case fold.
- A connection tries every eligible server once, least loaded first, and then the seed hosts, each once and in the order given, as the JDBC driver's `getConnection` does before it falls back to a plain connection to the hosts in its URL. There is no cap on hosts per connection, and a connection that fails everywhere returns the last error.
- With `load_balance` off, the hosts are tried in the order given, as pgjdbc does with `loadBalanceHosts` off: every connection goes to the first host that works, with `target_session_attrs => read_write` the first that accepts writes. The pool gathers its connections there, and moves them back to it, `rebalance_batch` at a time, once a refresh's probe finds it back.
- The seed hosts as a fallback while no discovered server is working, the first working seed first. When every seed has failed too, the seeds regardless of their failures, as the smart drivers fall back to a plain connection to the hosts in their URL. Under `only_primary`, `only_rr`, and `fallback_to_topology_keys_only` with topology keys, where the JDBC driver refuses instead, the seeds take no connection once servers are discovered, and a connection that finds no eligible server fails with `{no_node_available, primary | read_replica | cluster}`, whether or not it tried some servers first. Before a discovery has succeeded, and on PostgreSQL, every mode takes the seeds.
- Only a failure to connect marks a server down: the failures pgjdbc reports as SQLSTATE 08001, sorted by `eysql_error:connect_failure/1`. Such a server is left out of new connections until the first refresh after `failed_host_reconnect_delay_secs` (0 to 60 seconds; or after a delay that doubles up to `failed_host_max_delay_secs`, when that is set) finds it back, as in the smart drivers. A server that answers and fails the connection otherwise, such as with a failed login, too many connections, "starting up" or "shutting down" (57P03) or a failed TLS handshake, is listed as `rejected`, and is left out of new connections in the same way until a refresh's probe finds it taking connections again. The JDBC driver skips such a server for that one connection only; eysql keeps it out so that a server that turns connections away while it restarts comes back within one refresh of accepting them, rather than when a pooled connection next reaches `max_lifetime`. Nothing that happens on an open connection, a failed or cancelled query included, leaves a server out. A connection failure brings the next refresh forward, and a connection that finds no host does not. On PostgreSQL, where there is nothing to discover, refreshes run on the same schedule.
- A pool with lifetime recycling and rebalancing. It sends no query of its own: like the smart drivers, it has no health checks. It finds a dead connection when epgsql's process exits with its socket, or when a query on it fails with a lost connection. Idle connections past their lifetime close at the rebalance tick. Rebalancing moves at most `rebalance_batch` connections per interval, busy ones included, and a failed server keeps its connections. Connections move towards a server only once a connection to it has opened since it failed, so seeds behind a load balancer, and connections on a fallback level, stay put while better servers remain down. The pool starts its connections at once, and they wait for the first discovery in `eysql_cluster:open/1`. Only the process holding a connection can check it in or discard it. `stats/1` counts connections by state, `draining` included, and by host. `cluster_info/1` shows where new connections go (`placement`), which servers the pool keeps (`allowed`), the servers that are down (`failed`), and, apart from them, the standbys that `target_session_attrs => read_write` turned away (`read_only`) and the servers that failed a connection without being down (`rejected`).
- A failing server is logged once per run of failures, as a warning with the reason, and the end of the run at info. A run ends only once a connection has opened since the server's last failure and a minute has passed since it. A standby is logged at info, not as a warning. A server that turns from down to standby or rejected, or back, starts a new run, logged in words that say which, so a failed login never reads as a server that is down. Failed discoveries are logged by the same rules, once per run.
- Failed servers, whether down, standbys or rejected, are probed at the first refresh after their delay, with the `target_session_attrs` check: at most one probe per server, closed at once, not counted, and stopped after twice `connect_timeout` or when the cluster stops. A discovery that succeeds probes at once the ones that are due, so that after an outage they come back with the cluster. There are no timers per server, so a server that stays failed is tried once per refresh. A probe's error decides what the server counts as, so a server that answers 57P03 while it shuts down and then refuses connections turns from rejected to down, and takes connections again from the first refresh after it is back. After a password rotation the probes add one failing login per server per refresh.
- Discovery forgets the failures of servers it no longer lists.
- Each server's `host` or `public_ip`, chosen as the JDBC driver's `LoadBalanceService.refresh` chooses: the discovery resolves the name it connected to and each server's two addresses, and the first server whose `host`, or `public_ip`, is the address that answered, or whose two are the same address, decides for the life of the pool. Until then, `public_ip` is guessed when every server has one that resolves. The lookups run in the discovery's process, all at once, bounded by `connect_timeout`; a name that does not resolve matches nothing, and when the name the discovery connected to does not resolve, it moves on to the next host.
- `transaction/2,3` on the pool's driver, with retries on 40001 and 40P01, a random back-off between attempts capped by `max_backoff`, and `commit_outcome_unknown`. When a retry gets no connection, the result is the error that caused the retry.
- `socket_timeout`, in milliseconds, off (`infinity`) by default as pgjdbc's `socketTimeout` is. It bounds `equery/3`, `squery/2`, the BEGIN, COMMIT and ROLLBACK of `transaction/2,3`, and `eysql_conn:equery/3` and `squery/2` in the process that checked the connection out, as inside `with_connection` and `transaction`. A checkout hands the bound to that process; each call starts a timer to the pool and cancels it when the answer comes, sending nothing to the server. When a call runs out, the pool kills the connection, closing its socket, and the call returns `{error, {connection_lost, socket_timeout}}`; the pool opens another, marks no host and starts no refresh. A transaction cut off before COMMIT runs again, and one cut off during COMMIT returns `commit_outcome_unknown`. Unlike pgjdbc's, which bounds each read, it bounds the whole call. epgsql's own functions called on the connection are not bounded.
- `with_connection`, `equery`, `squery` and `transaction` close a connection left inside a transaction instead of returning it to the pool. `eysql_conn:transaction_status/1` reads the status without a round trip, inside the connection process, so it copies none of the connection's state.
- `with_connection`, `equery`, `squery` and `transaction` return their result when the pool stops while they hold a connection, instead of exiting. A transaction whose retry finds the pool stopped returns the error that made it retry.
- `target_session_attrs => read_write` for PostgreSQL with several hosts.
- eysql passes `ssl_opts` to epgsql unchanged, so OTP's certificate verification applies. It never adds `{verify, verify_none}`.
- The password is kept as given, as a binary or the caller's own zero-arity fun. The pool and cluster print their state with `password`, `ssl_opts` and `epgsql_opts` redacted, and the reason a failure is logged with hides passwords in proplists and under `password` keys, atom or binary, in maps.
- An invalid option is an error from `start_link`, not a crash. That includes `topology_keys` that are not keys, and text that is not a string or a UTF-8 binary, in a text option, a host or a topology key. The password need not be text.
